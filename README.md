# CS-255
System Analysis and Design Portfolio work for the DriverPass Project

DriverPass Reflection

The DriverPass project had to do with a client that wanted a system that could help manage driver training services. The system needed 
to support things like customer accounts, driving lesson appointments, training packages, practice tests, student progress, driver information and updates from the DMV. The goal was to design a web-based system that could be used by customers and employees while keeping that information organized and giving each type of user the access they needed.

I feel what I did well was taking those different requirements and turning them into designs that could easily be understood. Since there was a lot of information in the original requirements, I had to decide what belonged together and how the different users would interact with the system. The use case, activity, sequence and class diagrams helped show that system from the different points of view instead of trying to explain it all in one diagram. 

Something I would like to revise would be the class diagram because the main classes and information was there but there could be some improvement in the way some of those relationships are shown to make the diagram cleaner. After working with the other UML diagrams I believe I have a better understanding as to how important it is in keeping the design detailed enough to be useful without making it harder to read.

I interpreted the user's needs by going through the requirements and looking at what each person needed to be able to do in the system. Customers needed to manage appointments, choose training packages, take practice tests and view their progress while the employees needed different functions based on their roles. I used those needs to decide which use cases, classes and interactions needed to be included in the design. Considering the users needs because a system that technically works still isn't useful if it doesn't actually support those who are using it.

I think it helps to break the system into smaller parts before trying to look at everything at once when designing software. A good start would be to gather the requirements, identifying users and figuring out what the main things the system needs to do. I would then use the diagrams and models to look at the system from different angles and make sure the pieces work together. I will continue using use case, activity, sequence and class diagrams because of how each one helped me catch details I might have missed had I based everything solely on the written requirements.
